# CSS 与界面样式规范

本规范适用于桌面端 `src/` 和移动端 `mobile/src/` 的新增及修改样式。现有代码尚未完全符合规范；只在任务涉及的范围内逐步整理，不进行无关的全量迁移。用户明确要求的视觉效果与任务范围优先。

## 1. 样式组织

桌面端使用原生 CSS，`src/styles.css` 为全局入口，保持现有导入顺序：

| 文件 | 职责 |
| --- | --- |
| `src/styles/tokens.css` | 主题颜色、圆角、阴影等设计变量 |
| `src/styles/base.css` | 全局字体、盒模型、页面基础规则 |
| `src/styles/electron.css` | Electron 窗口相关样式 |
| `src/styles/layout.css` | 主布局与区域尺寸 |
| `src/styles/components.css` | 可复用按钮、表单、弹窗等公共样式 |
| `src/styles/features.css` | 业务功能样式 |
| `src/styles/responsive.css` | 桌面端响应式调整 |

修改已有组件时优先在原所属文件维护规则，避免在文件末尾不断追加同一选择器的覆盖。独立且较大的功能可使用同目录的专用 CSS，并通过组件或明确的入口导入。公共 Markdown 展示沿用 `src/styles/markdown-content.css`。

移动端目前使用 `mobile/src/styles.css` 和 provider 专用的 `opencode.css`、`codebuddy.css`。保持现有归属；这套样式尚未共享桌面主题变量。不要未经任务要求引入 Tailwind、CSS-in-JS、CSS Modules 或新的样式框架。

## 2. 设计变量与主题

- 桌面端颜色优先使用已存在的 `--color-*` 语义变量，圆角、阴影优先使用 `--radius-*`、`--shadow-*`。先检查变量是否存在，避免拼出未定义的变量并用 fallback 掩盖错误。
- 需要新公共变量时在 `tokens.css` 定义默认值，检查 `dark-blue`、`dark-green`、`light` 主题是否需要对应值；可继承的值不必重复声明。
- 业务品牌色、图表分类色、文档预览背景等有明确语义的固定颜色可以保留；普通背景、文字、边框与状态反馈优先使用主题变量。
- 移动端沿用当前视觉体系。重复新增的移动端颜色可提取为移动端语义变量，但不要为局部修改自动迁移全部固定颜色或直接引入桌面全局样式。
- 使用 `color-mix()` 派生透明底色时优先基于语义变量，确保文字仍有足够对比度。

## 3. 命名与作用范围

- 类名使用小写连字符，如 `.graphical-menu-item`；功能内的类名使用一致的模块前缀，避免新增 `.title`、`.content` 等容易冲突的全局类。
- 可复用公共类放在公共样式中；功能状态可沿用 `.active`、`.loading`、`.danger`，但应与所属组件类组合使用。
- 属性状态沿用组件已有的 `data-*`、`aria-*`。不要仅为样式再维护一份相同的 React 状态。
- 优先使用低权重类选择器；避免 ID 选择器、过深 DOM 链和依赖偶然结构的覆盖。覆盖第三方组件时用所属容器限定范围。
- `!important` 仅用于确有必要的第三方样式或明确优先级冲突，并说明原因；普通组件冲突应通过规则归属、选择器或导入顺序解决。

## 4. 格式与尺寸

- 新增规则使用 2 空格缩进，每条声明独占一行；局部修改沿用周围格式，不顺带格式化整个文件。
- 声明通常按布局与定位、尺寸与间距、边框与背景、文字、交互与动画排列；同一规则中保持一致即可。
- 新增间距优先采用 `4 / 8 / 12 / 16 / 24px`，紧凑工具栏可用 `2 / 6px`。这些是后续设计的推荐值，不是对现有尺寸的强制替换。
- 字号与控件尺寸优先复用所在区域已有值；不要在局部样式调整中改变整体界面密度。可重复复用的尺寸再提取变量，避免为每个数值建立 token。
- 静态外观放在 CSS 中；React 内联样式适合拖拽尺寸、运行时坐标、进度和动态 CSS 变量等依赖数据的值。

## 5. 布局、移动端与交互

- Flex/Grid 中承载长文本的子项按需设置 `min-width: 0`；可滚动的纵向区域按需设置 `min-height: 0`，避免内容撑开主布局。
- 根据内容选择省略、换行或局部滚动。代码块、表格、路径和长模型名不能导致整个页面横向溢出；不要用全局隐藏溢出掩盖布局问题。
- 弹窗尺寸结合可用视口，保留内容滚动与操作区可达性；新增层级应参考现有 overlay，避免随意叠加极大 `z-index`。
- 移动端保留 `100dvh`、安全区 `env(safe-area-inset-*)` 和底部输入区保护。触控按钮优先保持约 `40–44px` 的可点击区域；紧凑操作沿用区域既有尺寸，不机械套用桌面尺寸。
- 提供可见的键盘焦点、hover、disabled 与 loading 状态；图标按钮保留或补充准确的 `aria-label` / `title`。状态信息不能只依靠颜色区分。
- 引入持续或大幅动画时考虑 `prefers-reduced-motion`，不让动画阻碍输入和操作。
- 公共交互同时涉及桌面和移动端时检查两端对应样式；仅针对一端的任务不要自动扩大为两端改造。

## 6. 修改与验证

修改前检查当前组件、样式归属、共享类及主题变量，确认规则影响范围；只修改任务涉及的内容，不改动生成目录 `dist/`、`release/`。

代码改动后运行相关端的测试与构建：桌面端 `pnpm test:desktop`、`pnpm build:desktop`；移动端 `pnpm test:mobile`、`pnpm build:mobile`。两端均受影响时运行 `pnpm test`、`pnpm build`。纯文档或技能改动不需要应用测试和构建。

视觉检查关注深浅主题、窄视口、长文本、弹窗滚动、键盘焦点及移动端安全区。没有实际运行界面时，明确说明视觉和 Electron/设备运行时验收尚未完成；测试与构建通过不能代替视觉验收。不需要为验证启动 dev 模式。

仓库目前没有 Stylelint 或 CSS 自动格式检查；本规范通过开发与评审执行，引入自动检查需另行纳入任务范围。
